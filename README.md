## Зачем это нужно

«Быстро», «удобно» и «при необходимости» звучат как требования, но не задают поведение. Разработчик трактует их по-своему, тестировщик пишет тест по-своему — расхождение всплывает на демо.

ReqLens делает первичную вычитку за секунды: вставляете ТЗ, user stories или критерии приёмки — получаете замечания с пояснениями, оценку и отчёт, который можно приложить к задаче.

LLM здесь не используется намеренно: правила детерминированы, объяснимы и не требуют отправлять текст наружу. Подробнее — в [статье](https://github.com/IKatsubo13/ReqLens/blob/main/docs/habr-article.md).

## Возможности

- **Проверка на лету** — результат обновляется во время набора текста.
- **15 правил** — неоднозначности, неопределённость, пассивный залог, атомарность, дубли и структура.
- **Оценка 0–100** — нормируется на число требований, чтобы большой документ не проигрывал только из-за размера.
- **Подсветка** — проблемные места видны прямо в документе.
- **Разбор без шума** — однотипные замечания группируются, у каждого есть объяснение и рекомендация.
- **Markdown-отчёт** — копирование и скачивание одним кликом.
- **Три демо-документа** — плохое ТЗ, хорошее ТЗ и интеграция с API.
- **Локальность** — без бэкенда, аналитики и внешних запросов; можно загрузить `.md` или `.txt`.

## Быстрый старт

Нужен Node.js 22+.

```bash
npm ci
npm run dev
```

Промо откроется на `http://localhost:5173/`, линтер — на `http://localhost:5173/app.html`.

```bash
npm test        # тесты движка (Vitest)
npm run lint    # oxlint
npm run build   # production-сборка в dist/
npm run preview # локальный просмотр сборки
```

## Как устроено

```text
src/
  linter/
    engine.ts      — парсинг требований, сигналы, оценка, сборка результата
    rules.ts       — словари и правила (термины, атомарность)
    report.ts      — Markdown-отчёт
    types.ts       — типы предметной области
    engine.test.ts — тесты движка
  components/      — интерфейс: редактор, оценка, проблемы, разметка, отчёт
  data/examples.ts — демонстрационные документы
  promo/           — лендинг и его стили
docs/
  habr-article.md  — статья для Habr
  images/          — скриншоты для README и статьи
```

- **Парсинг.** Документ разбивается на требования: списки, нумерованные пункты, маркеры `US-1` / `AC-1`, абзацы. Заголовки и названия разделов исключаются.
- **Правила.** Чистые функции со словарями стемов и регулярными выражениями. Каждое замечание содержит важность, объяснение и рекомендацию.
- **Оценка.** Штраф за замечания нормируется на число требований: ошибка — 10, предупреждение — 5, подсказка — 1.5. Итог ограничен диапазоном 0–100.
- **Интерфейс** не знает о правилах: получает готовый `LintResult` и отображает его.

Добавить правило — значит описать группу терминов или отдельную проверку и подключить её в `lint()`. Тестовый пример лежит рядом.

## Дизайн

Промо и приложение оформлены в одном стиле ризографии: тёплая бумага, флуоресцентный розовый и глубокий синий, офсетные тени и полутоновые точки.

В интерфейсе линтера крупные заголовки Unbounded соседствуют с моноширинным документом. Документ выглядит как лист для правок: бумажная фактура, синие линейки и розовая линия поля. Оценка сделана в виде штампа, замечания — как маргиналии на полях.

Все шрифты — Unbounded, IBM Plex Sans и IBM Plex Mono — подключены локально через Fontsource: внешних запросов за шрифтами и аналитики нет.

## Тесты и CI

В проекте 8 тестов движка на Vitest. GitHub Actions запускает тесты и сборку, а затем публикует сайт на GitHub Pages. Проверка кода локально — `npm run lint`.

## Деплой

Сайт публикуется автоматически из ветки `main`:

- [Промо-страница](https://ikatsubo13.github.io/ReqLens/)
- [Линтер](https://ikatsubo13.github.io/ReqLens/app.html)

В настройках репозитория выбран **Settings → Pages → Source: GitHub Actions**. Для форка достаточно включить этот источник: workflow `.github/workflows/deploy.yml` уже лежит в репозитории, а `base: './'` позволяет работать из подпапки.

## Ограничения

- Это эвристики, а не замена ревью: возможны ложные срабатывания и пропуски.
- Смысловые противоречия между требованиями не ловятся, если они не выражены словами-маркерами.
- Словари ориентированы на русский язык; английские термины поддержаны частично.
- Оценка — ориентир для приоритизации, а не формальный стандарт качества.
- Пока нет истории проверок, совместной работы и интеграций с Jira или Confluence.
